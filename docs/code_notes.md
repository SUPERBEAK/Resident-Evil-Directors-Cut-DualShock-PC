# Code notes

This document describes how the decompiled source code in `dualshock/` is organized and named: the
source tree, the headers and configs, the naming conventions and where the names come from, the
different ways the code reaches fields and fixed addresses, the C forms that look odd but must stay for
the byte match, and the readability and structure tools that rewrite the code safely.

[decomp_guide.md](decomp_guide.md) is the short version: the tool table, the build commands, the naming
conventions in brief and the folder layout. This document goes into the details behind it. How to write C
that GCC 2.6.3 turns into the original code is in [matching_guide.md](matching_guide.md); how the game
itself works (RAM layout, scratchpad, scripts) is in [game_notes.md](game_notes.md); the project-level
tools are in [tools_detailed.md](tools_detailed.md).

Paths are relative to `dualshock/` unless they start with `dualshock/`, `tools/` (the project scripts at
the repository root) or `docs/`.

## State of the sources

- Every function and global in `src/` and `include/` has a real name: no `func_XXXXXXXX` and no
  `D_XXXXXXXX` is left. Every old/new pair with its evidence is recorded in the `config/names_*.txt` and
  `config/globals_*.txt` files (for example `config/globals_main_3.txt`).
- All code and data is C: no `INCLUDE_ASM` or `INCLUDE_RODATA` is used (see "Data in C" in the
  [matching guide](matching_guide.md)).
- The build prints no compiler warnings; a new warning usually means a real mistake.
- Both generated struct headers (`re1_views.h`, `re1_locals.h`) regenerate byte-identically from their
  specs, and a fresh `asm/` tree (split + build) matches all 13 executables.
- After any change, `make` must still print `All 13 executables match the originals.`

Function addresses in this document (`func_8005905C`, ...) are the original addresses; the current name
follows in parentheses where there is one. `config/symbol_addrs.txt` maps every address to its name.

## Source tree

### Top level of `dualshock/`

| Path | Content |
|---|---|

| `config/` | symbol files (`symbol_addrs.txt`, `symbol_addrs_psyq.txt`, per-overlay files) and the other configs (see [Configs](#configs)) |
| `include/` | shared headers (see [Headers](#headers)) |
| `src/<program>/` | C sources of each program |

| `tools/` | the decomp's Python tools |
| `Makefile` | the build and checksum check (see the [matching guide](matching_guide.md)) |

| `asm/`, `build/`, `assets/` | generated by `make split` / `make`; not committed |

### What is committed and what is generated

Committed: the YAML configs, `config/`, `include/`, `src/`, `tools/`, `Makefile`.

Ignored by `dualshock/.gitignore`: `asm/`, `build/`, `assets/`, `*.ld`, `undefined_*_auto.txt`. All of
these are derived from the copyrighted executables and are regenerated by `make split`. m2c's
`include/m2c_macros.h` is also not committed (it is GPL-3.0 licensed); `tools/m2c_macros.py` downloads it at
the pinned m2c commit. `include/include_asm.h` (the `INCLUDE_ASM` / `INCLUDE_RODATA` macros) must have LF line
endings; `dualshock/.gitattributes` forces LF.

### How a C file starts out (splat)

splat generates a C file with one `INCLUDE_ASM` line per function and `INCLUDE_RODATA` lines for data, plus
the empty functions it decompiles automatically. The main program started as one such file,
`src/main/capcom.c`, with 949 `INCLUDE_ASM` lines, 6 `INCLUDE_RODATA` lines and 13 empty functions.
Decompiling a function means replacing its `INCLUDE_ASM` line with matching C. splat never overwrites an
existing `.c` file; delete it (only if it holds no work) to regenerate it.

### One C file per executable, Capcom's many source files

Capcom built each executable from several source files. When the code was one C file per executable
(`capcom.c` for the main program, one `stageN.c` per stage), that single-file layout had to model the
traces of Capcom's file boundaries: the same global declared with different types, callers that saw other
prototypes, rodata pad words where a file ended (see [Declarations and aliases](#declarations-and-aliases)
and [Forms that look odd but must stay](#forms-that-look-odd-but-must-stay)). Splitting into topic files
helps with `static` functions and readability; the topic files below are the result.

### Main program: topic files

The main program (`SLUS_007.47`) is split into topic files in `src/main/` (`door.c`, `effect.c`, `scd.c`,
`player.c`, `sound.c`, `status_menu.c`, `npc.c`, `movie.c`, `item.c`, `inventory.c`, `camera.c`, ...). They
were split from the one `capcom.c` by `tools/splitc.py` and later refined with `tools/splitfile.py` (see
[Topic files](#topic-files-splitplanpy-splitcpy-splitfilepy)). Each file starts with a comment saying what it
holds; key functions have one-line comments.

The old prelude of the single original file (the globals block, the file-scope types) is the shared header
`src/main/globals.h`, which every topic file includes.

Each topic file starts with file-scope prototypes of the functions defined in **earlier** files that it
references, plus copies of the file-scope types those prototypes use. Functions defined in later files stay
unseen. This reproduces exactly what each function saw when everything was one file (a definition earlier
in the same file), which the byte match depends on. The rodata alignment rules that decide where a file may
start are in the [matching guide](matching_guide.md).

A typical topic file starts like this:

```c
/* door.c - The door transition: the door script interpreter (door_op_*: model draw order, camera, moves,
   fades, sounds) and the door animation start / update. */
#include "common.h"
#include "psyq_types.h"
#include "re1_types.h"
#include "globals.h"
```

### Stage overlays: one file per enemy

Each stage overlay `src/stageN/` has:

- `entry.c` - `stageN_entry`, the first code of `STAGEN.EXE`: it installs the stage's enemy update table,
  the player animations its enemies override, and the BGM / voice / background tables, then ends its task;
- one file per enemy;
- `src/stageN/globals.h` - that overlay's declarations.

The other overlays (`logo`, `prologue`, `title`, `select`, `ending`) have their own folders under `src/`.

| stage | enemy files |
|---|---|
| stage1 | cerberus, crow, monster_plant, zombie |
| stage2 | crow, yawn, zombie |
| stage3 | adder, black_tiger, cerberus, hunter, tyrant |
| stage4 | monster_plant, neptune, plant42, plant42_roots, wasp, web_spinner, zombie |
| stage5 | chimera, computer_arms, tyrant, zombie |
| stage6 | crow, hunter, monster_plant, web_spinner, zombie |
| stage7 | crow, hunter, yawn, zombie |

### Shared enemy code and wrappers

Capcom linked one enemy source into every stage that has that enemy. `src/shared/<enemy>.c` holds that code
once (zombie: 6 stages; crow: 4; hunter, monster_plant: 3; cerberus, yawn, tyrant, web_spinner: 2 each).
Every enemy that appears in more than one stage is shared. Each `src/stageN/<enemy>.c` is a small wrapper:

```c
/* zombie.c (stage1) - compiles the shared zombie code (src/shared/zombie.c) into STAGE1.EXE with this
   stage's declarations (globals.h). */
#include "common.h"
#include "psyq_types.h"
#include "re1_types.h"
#include "globals.h"
#include "../shared/zombie.c"
```

plus prototypes of earlier files and the file's rodata padding line, if it had any. Shared files are not
compiled on their own: the Makefile only builds `src/<program>/*.c`, and the C object rule depends on
`src/shared/*.c`. When a stage file only contains `#include "../shared/<enemy>.c"`, read the code in
`src/shared/`.

The per-stage copies differed only in **declarations**, not code. Each stage's `globals.h` has the type of
that overlay's first declaration of a global: the player's hit-state byte at 0x800C51AE was declared `u8` in
stages 1/4/6 and `s8` in 2/3/5/7; the player's joint pointer at 0x800C51BC was `void *` in some stages and
`s32` in others. In the shared text, every global whose `globals.h` declaration differs between the sharing
stages gets a private typed alias with the canonical stage's type in each function that uses it:

```c
extern u8 zombie_stagger_tbl_u8[] __asm__("zombie_stagger_tbl");
```

With that, one text matches everywhere, even where a stage's own copy had different temporaries or braces
(equivalent code). The shared files are written by `tools/sharetwins.py` (see
[Twins across overlays](#twins-across-overlays)).

### `globals.h` files

- `src/main/globals.h`: declarations shared by all main-program files (the old prelude of `capcom.c`).
  It also holds file-level typedefs such as `Str6` (`typedef struct { char s[6]; } Str6;`), used for
  by-value copies of the 6-byte `"bu00:"` memory-card path.
- `src/stageN/globals.h`: one include of `include/stage_common.h` (everything common to the stage overlays);
  each enemy declares its own data at the top of its source.
- The other overlays have their own `globals.h` as well.

## Headers

### Header overview (`include/`)

| Header | Content |
|---|---|
| `common.h` | basic types |
| `psyq_types.h` | PsyQ (Sony SDK) types, included by every source file. Struct sizes are verified: MATRIX 0x20, DRAWENV 0x5C, GsCOORDINATE2 0x4C, GsSPRITE 0x24, GsOT 0x14 |
| `psyq_protos.h` | prototypes of the Sony functions the Capcom code calls. Flattened into `build/m2c_context.h` as m2c context |
| `re1_types.h` | Capcom's structs (`Entity`, size 0x18C; `PlayerWork`, `Billboard`, `Effect`, `MenuWork`, ...), the exact-form access macros (`ENEMY_*`, `ENTITY_*`, `MEMBER_AT`, `FIELD_AT`, `MEMBER_AS`, `FIELD_OF`, `FIELD_OF_AS`, `OFFSET_MEMBER`, `OFFSET_DEREF`) and constants. Included by every source file; it includes the generated headers below |
| `re1_flags.h` | flag, pad and sound constants (see [Named constants](#named-constants)) |
| `overlay_api.h` | the `api_*` pointers and `g_ApiCallPtr`, declared once; `API_AS(T, f)` |
| `stage_common.h` | everything common to the stage overlays |
| `re1_externs.h` | typed globals (`extern Entity *g_CurrentEntity;`). Not included by the source files: used as m2c context and copied into function bodies by `integrate.py` when a new function uses them |
| `re1_views.h` | **generated** by `tools/structview.py` from `config/structs/*.txt` |
| `re1_locals.h` | **generated** by `tools/localview.py` from `config/locals/*.txt` |
| `re1_addrs.h` | **generated** by `tools/litaddr.py` from `config/addrs.txt`: `ADDR_name` plus the `LIT(...)` / `LITP(...)` macros; included by `re1_types.h` |
| `m2c_fields.h` | only for decompiler drafts (`tools/autodecomp.py`); no file in `src/` includes it. It adds this project's two field-access forms (`M2C_SFIELD`, `M2C_PFIELD`) and the `M2C_FIELD` selection to m2c's own `m2c_macros.h` |
| `m2c_macros.h` | m2c's macros, not in git (downloaded by `tools/m2c_macros.py`); not included by any source. Its two live macros exist as `OFFSET_MEMBER` / `OFFSET_DEREF` in `re1_types.h` |
| `include_asm.h` | the `INCLUDE_ASM` / `INCLUDE_RODATA` macros (LF line endings required) |
| assembly helpers | `macro.inc`, `labels.inc`, `gte_macros.inc` |

The generated headers regenerate byte-identically from their specs. **Edit the specs, never the generated
headers.**

Edit headers with an editor, not with `sed` or shell heredocs: writing `\` + newline through a heredoc
mangles macros.

### Named constants

- `include/re1_flags.h`: status flags `STATUS_*` (`STATUS_ADVANCED`, `STATUS_IN_WATER`, ...), game state
  flags `GAME_*` (`GAME_MIRROR_ON`, ...) plus `MENU_REQUEST(MENU_MODE_x)`, pad bits (`PAD_*` such as `PAD_RUN`
  are the game's action bits, `PSX_*` the raw controller bits), menu sounds `SE_MENU_*` (`SE_MENU_CONFIRM`).
  Every bit of `g_StatusFlags` / `g_GameStateFlags` the code uses has a name. Single-bit clears are written
  inverted: `&= ~STATUS_DOOR_WAIT_BGM` for `&= 0xFF7FFFFF`, `& ~GAME_SCREEN_MODE` for `& 0x3FFFFFFF`.
- `include/re1_types.h`: `MENU_MODE_*`, `FMV_*`, sizes `ENTITY_SIZE` (0x18C), `JOINT_SIZE`, `EFFECT_SIZE`
  (0x84), `EFFECT_AT()` (raw pool offsets), `ROOM_CAMERA_VIEW(_ADDR)`, `BYTES(n)`.
- Overlay constants: `STATE4()` for the 4 state bytes written at once, `JOINT_N(joints, n)` / `JOINT_N*()`,
  `g_StageRoom` + `STAGE_ROOM()`, per-enemy sound ids (`ZOMBIE_SE_*`, e.g. `ZOMBIE_SE_GROAN`) and scenario
  flags (`SCN_FLAG_*`, e.g. `SCN_FLAG_PLANT42_DEAD`).

```c
#define STATE4(state, sub, behavior, action) ((action) << 24 | (behavior) << 16 | (sub) << 8 | (state))
#define STAGE_ROOM(stage, room) ((room) << 8 | (stage))
#define MENU_REQUEST(mode)       (0x4000 >> (mode))
#define BYTES(n) struct { u8 b[n]; }
```

Bits whose meaning is not clear stay numbers.

### Overlay API

Overlays call the main program through a table. The call idiom is

```c
(g_ApiCallPtr = api_RotMatrix)(...);   /* calls RotMatrix; g_ApiCallPtr = 0x801FEC18 */
```

Every `api_*` pointer is declared once in `include/overlay_api.h`; `API_AS(u32, api_rand)(...)` marks the
few calls whose result Capcom's code read as another type. The API table (183 entries at 0x801FE900) is
decoded by `tools/api_table.py`, which can write it as a Markdown table (`--md <file>`,
`overlay_api_table.md`).

## Naming conventions

### Functions, globals, types

- **Functions**: `snake_case` (`pad_update`, `zombie_chase_player`, `itembox_draw`, `zombie_update`,
  `room_set`, `game_loop`). Where the RE1 PC decompilation has the same function, its name is used, so the
  two can be read side by side.
- **Globals**: `g_Name` (as in the PC decomp's PSX docs: `g_CurrentEntity`, `g_PlayerEntity`,
  `g_GameStateFlags`). Pointer globals may use `g_pName` (`g_pScdEventCurrent`). String constants use
  `s_Name` (`s_Empty`, `s_MemcardTitleJill`, `s_SaveFileName`, `s_YesNo`).
- **Types**: `PascalCase`.
- **A single field of a known block**: `<block>_<Field>` (`g_MapScreen_Room`, `g_StatusScreen_FilePage`).
- **Written but never read** globals get neutral names (`g_XaGetlocSpare`, `g_SndFadeEndDelay`,
  `g_UnusedInitWord`).
- **Overlay API slots**: `api_<main-program target>`.
- **Stage entry**: `stageN_entry`.
- **Overlay `__main` stubs**: the empty `jr ra` stub every overlay entry calls first is that overlay's copy
  of GCC's `__main` hook: `title__main`, `stage1__main`, ...
- **Main-program player symbols**: `g_Player` + the field name in CamelCase (`g_PlayerHitState`,
  `g_PlayerHealth`, `g_PlayerPoisonTimer`, ...). They are the same bytes as `g_PlayerEntity.<field>` (see
  [Entity and player](#entity-and-player)).
- **Typed aliases**: `<name>_<type suffix>` (`zombie_stagger_tbl_u8`, `g_DoorCmdCur_voidp`,
  `g_XaVolume_s32`). Per-function function aliases: `<name>_l`; other suffixes in use are `_p`, `_a1` and
  `_u8` (see [Declarations and aliases](#declarations-and-aliases)), and `_v` (`Flg_on_v`, `joint_move_v`).
- Names on the same twin code may be the same in several overlays; that is fine because each overlay
  links on its own.

### Overlay names

- Overlay names follow one scheme: one style for prefixes, `_tbl` for tables, `_nop` for stubs,
  `<enemy>_sca_info`, `behavior`. Twin enemies (web spinner / black tiger) use the same scheme.
- Stub names say which table slot they fill (e.g. `message_action_none`).

### Special cases

- Four PsyQ library functions the signature matcher missed are named by hand: `GsSetProjection`,
  `GsSetWorkBase`, `SsUtKeyOn`, `SsUtAllKeyOff` (medium confidence; they sit in a block of libsnd functions
  between `SpuVmGetProgPan` and `_SpuInit`).
- Two zero words splat had labelled as functions are data: `g_TitleTimers` (base of the `TITLE_TMR` view)
  and `g_LogoStrDecodeX`.
- `g_PlayerEntity` (0x800C5124) keeps an `__asm__` alias for the overlays.
- An address can have a second name for another use (`g_ScdByteVars` / `g_ScdWordVars`: the SCD variable
  banks).

### Struct fields

- Fields that have a PC decomp name keep it where it fits; where the meaning differs, the PC name is kept
  in a comment (e.g. `Entity.sub_state`, the second-level state index).
- Field names starting with `pad<hex>` / `sub<hex>` are treated as padding by `structview.py` (not names
  like `substate`).
- Never-read fields (only cleared or set at init) are named `unused_<offset>` (in an enemy work area: the
  entity offset), e.g. `unused_01` / `unused_13`.

### Local variables and parameters

Decompiler names (`sp18`, `temp_v0`, `var_a1`, `arg0`) are gone from code; no function definition has an
`argN` parameter, and prototypes use the definitions' parameter names. Conventions:

- reloads of `g_CurrentEntity`: `e`, `e2`, ...;
- joint arrays `joints`, one joint `joint`;
- distances `dx` / `dz` / `dist`;
- SCD script pointer `p`, door script `op`;
- never-read locals `unused`.

The local-pointer specs name variables per function (`param <function> <variable or expression>`); after
renaming locals, update those lines with `specvars.py` (see [Renaming](#renaming-renamepy-ovlrenamepy)).

### Local type names

Local typedefs are named after what they hold (`EffectActor`, `ScdEventView`, `MovieEntry`, `ShotEffect` /
`FireHit`, `MapScreenView`, `ClipJoint`, `JointView`, `AtkEnt`, `SelPlayer`). No type name carries an
address suffix (`RoomActionEntry`, `RdtCameraView`, `DoorCmdRec`, `STATE_BLOCK`, ...). A few records whose
use is still unclear keep neutral names (e.g. `RecB12_h17`). Fixed-size byte blocks that the matching code
copies by value are written with `BYTES(n)` and a comment.

Many local typedefs are layout copies of known structs, because the original code saw the same bytes
through another view: `Effect` (several effect views, including one starting at `g_EffectPool - 0x24`),
`EffectAnimStep`, `Entity`, `ScdEvent`, `TaskSlot`, `CdFileEntry`, `ClWindow`, `ClQuad`, `MapScreen`,
`DoorCmd`, `Joint` (the ejected magazine clip at joints + 0x744), `ClutFadeEntry`, RECT / TILE / GsSPRITE,
`RdtCamera`, `StHEADER` (the STR sector header).

Header struct sizes can be shorter than the real strides (GsDOBJ5 / GsCOORDINATE2 in `func_8002FB30`
(`item_viewer_draw_model`)); such functions use a local struct of the real size.

The 0x84-byte record table at 0x800C3024 was first called `Ply84`; it is now the `Effect` type in
`include/re1_types.h` (`g_EffectPool`). The rewrite tool `tools/ply84.py` keeps the old name.

## Where names come from

- Names may come from the RE1 PC decompilation (names only, never code).
- The PC decomp's docs (`docs/PSX_*.md`) analyse the 1997 Director's Cut `SLUS_005.51`. Its RAM/BSS addresses
  are the **same** as ours (`g_CurrentEntity` 0x800CAB14, the inventory 0x800C8784, `g_StatusFlags`
  0x800C3004, `g_GameStateFlags` 0x800C3000, the character id 0x800C5125, ...), so globals can be named by
  address. Code addresses differ (their `main` is at 0x80031954, ours at 0x80031F0C), so functions are
  matched by behaviour. Stage overlays load at 0x80105400 in both.
- The PC decomp's `PSX_ENGINE_ANALYSIS.md` (original PS1 release) addresses map onto ours with a slowly
  drifting offset: +0x5A8..0x5BC around 0x80030000-0x80031A58, about +0x6DC in the message code, +0x17AC in
  the player code (the jump is the DualShock pad/vibration code).
- Title overlay globals sit 0x50A after the Director's Cut addresses (`g_TitleMenuChoice` 0x800E1C00, ...).
- Address mappings between the PC port and PSX RAM: menu work block PSX = PC + 0x7F5D2698; game state PSX
  0x800C8660 = PC 0x00BE9820.
- The DC stage addresses in the PC docs do **not** apply directly to the Dual Shock overlays (they are
  shifted). Stage overlay functions are anchored on data and tables instead:
  - PC constant tables (health / stagger / ... byte patterns) are found verbatim in each `STAGEn.EXE`;
  - each stage's init sets `g_EnemyUpdateTable = &enemies_update_functions_tbl` (index = entity id, PC
    `EntityCommon.cpp`), which gives `<enemy>_update`;
  - each `<enemy>_update` dispatches `tbl[g_CurrentEntity->state]()`, which pairs with the PC enemy's state
    table by position (`hunter_state_table`, `bt_state_table`, `wsp_state_table`, `s_rootsStateTable`,
    `s_mpState`, `chimera_state_table`, `s_tyrantStates`; the zombie from the zombie_states / behaviour /
    damage / action / move / scd tables of PC `Zombie.cpp`).
- The PC decomp's `src/game/Entities.h` has the object layout with offsets that match ours; the Entity field
  names come from it.
- Twin functions across overlays get the same name (`nametwins.py`), and dispatch tables are paired with
  the PC namesake's table (`tableprop.py`); see [Names across overlays](#names-across-overlays).

## Fixed RAM addresses and the scratchpad

Capcom's code often reached globals through their address instead of the symbol, and that changes the
machine code, so the matching C has to do the same. A declared symbol produces `addu $at,$at,$reg`; the
original's numeric form produces `addu $at,$reg,$at`. Both appear in the original code, so each access keeps
the form it needs (details in the [matching guide](matching_guide.md)). A test converting the fixed
addresses to symbols broke the match almost everywhere.

`litaddr.py` names these numbers without changing the code:

```sh
python tools/litaddr.py header     # config/addrs.txt -> include/re1_addrs.h
python tools/litaddr.py apply      # rewrite src/ to use the names (then build: all 13 must match)
python tools/litaddr.py unnamed    # list literal addresses in src/ that have no name yet
```

`config/addrs.txt` lines are `0xADDRESS name [programs] # evidence`. `programs` is a comma list (`main`,
`shared`, `stage1`, `title`, ...) for when the same number means different things in different programs
(default: all). `include/re1_addrs.h` (included by `re1_types.h`) gets `#define ADDR_name 0x...` plus

```c
#define LIT(T, name) (*(T *)ADDR_##name)
#define LITP(T, name) ((T *)ADDR_##name)
```

`apply` rewrites:

| original                     | named                          |
|------------------------------|--------------------------------|
| `*(T *)0x800C8660`           | `LIT(T, g_StageId)`            |
| `((Effect *)0x800C3024)`     | `LITP(Effect, g_EffectPool)`   |
| `(T *)0x800C88A0` (no deref) | `LITP(T, g_OrderingTables)`    |
| `0x800C5158` (anything else) | `ADDR_g_PlayerPosX`            |

Read `LIT(u8, g_StageId)` as "the byte at g_StageId's address", `LITP(Effect, g_EffectPool)[i]` as a pointer
to that address, and `ADDR_g_PlayerPosX` as the address itself. The macros expand to the same tokens (plus
parentheses), so the build cannot change. No RAM or scratchpad address is written as a number in `src/`
(only in a few comments).

Parser rules the tool follows:

- a `)` before `*` is a cast only if it encloses a type;
- `(` glued to a name is a call (its parentheses stay);
- `*LITP(T, n)` may become `LIT(T, n)` only when no postfix operator follows: `*LITP(Prt84, p)[i].x80`
  dereferences the whole `[i].x80`.

The struct specs use the same forms: view macros are written with `LIT` / `LITP` (`CURRENT_ENTITY_LIT`,
`EFFECT`, `NPC_CUR`, `WS_WEB_CUR`, `END_TBLK`), and the regex `source` / `expr` lines (entity, effect,
task_slot, stage_entity) accept both forms.

### Scratchpad names (`sp_`)

The PS1's 1 KB scratchpad (fast RAM at 0x1F800000) is named the same way, in the "scratchpad" section of
`config/addrs.txt` (the tool's number regex covers 0x1F80xxxx). A line can carry two names:

```
0x1F8003D0 sp_vec / sp_vec_vx # temporary VECTOR ...
```

The second (scalar) name is used where the code dereferences the address as a number or pointer
(`*(s32 *)0x1F8003D0` -> `LIT(s32, sp_vec_vx)`), the first for the object (`(VECTOR *)0x1F8003D0` ->
`LITP(VECTOR, sp_vec)`, bare -> `ADDR_sp_vec`). Both are `#define`d. Other examples:
`LITP(GsSPRITE, sp_sprite)->x`, `LITP(MATRIX, sp_matrix)`, `LIT(s32, sp_tmp1C)` (per-function temporaries).
`SCRATCH->field` (the `Scratchpad` struct) is the struct form where the original used one, and
`SCRATCH_VEC` covers 0x1F8003D0. The scratchpad layout is described in [game_notes.md](game_notes.md).

`*(VECTOR *)LITP(void, sp_vec)` is written as `LIT(VECTOR, sp_vec)` (also for MATRIX).

## Field access forms

### Typed structs first, exact forms where needed

Typed structs replace raw offsets. With `Entity` in `re1_types.h` and `extern Entity *g_CurrentEntity;` as
context, m2c writes `g_CurrentEntity->routine1 = 1;` instead of a field macro. At `-O0` this compiles the same
as the struct-form macro, so overlay code can use real struct members freely.

Typed structs are a readability pass for code that already matches: rewrite, then verify that the build is
still byte-identical. The struct tools (`localview.py`, `structview.py`, `enemywork.py`) turn byte-offset
accesses into member names, verified per function: readable form -> exact form -> old text. The variables
keep their original types; the macros only name the fields.

### The two access forms and why both exist

The same field access compiles differently in struct-member and pointer-arithmetic spelling:

- **Member form** (m2c's `M2C_SFIELD`, now `OFFSET_MEMBER`): a real (anonymous) struct member,
  `sb $v1,0x85($v0)`. In the main program (-O2), GCC's MEM_IN_STRUCT_P flag decides whether a fixed-address
  load may be hoisted above stores through a pointer, so some pointer accesses must use this form
  (`tools/sfield.py`).
- **Pointer form** (m2c's `M2C_PFIELD`, now `OFFSET_DEREF`): pointer arithmetic, `addiu base,off; move;
  lh 0(..)` (array-element style). It was used for Entity fields at 0x170+ and the stages' engine call
  argument; in the main program the struct form changes -O2 scheduling for some accesses (e.g.
  `func_80038F7C` (`set_ladder_zone`)).
- m2c's `M2C_FIELD(base, T *, off)` is a plain cast access at a fixed offset; `include/m2c_fields.h` selects
  between the forms for decompiler drafts.

The exact forms in `re1_types.h` are built on the two:

```c
#define OFFSET_MEMBER(expr, type_ptr, offset) /* member form through an anonymous padded struct */
#define OFFSET_DEREF(expr, type_ptr, offset) (*(type_ptr)((s8 *)(expr) + (offset)))
#define MEMBER_AT(p, W, path, T)    OFFSET_MEMBER(p, T *, PATH_OFF(W, path))
#define FIELD_AT(p, W, path, T)     (*(T *)((s8 *)(p) + PATH_OFF(W, path)))
```

`MEMBER_AT(p, Joint, [1].flags, u8)` / `FIELD_AT(p, Joint, [1].flags, u8)` are the exact spelling where the
readable `JOINT(p)[1].flags` compiled differently; the offset is computed from the field path. Examples
written by hand:

- `FIELD_AT(r - 8, POLY_FT4, ->tpage, s16)` (POLY_FT4 walkers);
- the zero translation of the identity matrix used to clear a VECTOR:
  `FIELD_AT(g_DeadMoveValue, MATRIX, ->t, VECTOR)` (`g_DeadMoveValue` = `&g_IdentityMatrix`).

Some accesses must stay in macro or cast form: in draft form, the Entity sub-structure at 0x16C is reached
as `M2C_FIELD(((u8 *)D_800CAB14 + 0x16C), u8 *, k)`. A direct struct member compiles to a direct offset, and
`D_800CAB14 + 0x16C` on an `Entity *` would scale by sizeof(Entity) = 0x18C. The enemy work macros (below)
are the readable form of this area.

### Entity and player

- `g_CurrentEntity` is an `Entity *`; its fields are written `g_CurrentEntity->field`
  (`g_CurrentEntity->action_state`).
- The player is the Entity `g_PlayerEntity` at 0x800C5124 (`extern Entity g_PlayerEntity
  __asm__("D_800C5124");` in the overlays); its fields are `g_PlayerEntity.field` (`g_PlayerEntity.pos_x`).
- The player's own data from byte 0x15C on is `g_PlayerWork` (`poison_timer`, `max_health`, ...).
  `g_PlayerWork` is a macro, not a symbol, because a symbol at 0x800C5280 is not defined in programs whose
  original code never used it:

  ```c
  #define g_PlayerWork (*(PlayerWork *)((u8 *)&g_PlayerEntity + 0x15C))
  ```

- In the main program there are also `g_PlayerHitState`, `g_PlayerHealth`, ...: the same bytes as
  `g_PlayerEntity.hit_state`, `.health`, but separate symbols, because at -O2 a struct field is reloaded on
  every access there and the separate symbol is not. The original code compiled like separate globals there.
- Exact entity forms: `ENTITY_AS(e, f, T)` (member form) and `ENTITY_FIELD(_AS)` (pointer form) for fields
  read with another type; `ENTITY_STATE_WORD` / `ENTITY_ACTION_*(&g_PlayerEntity)` for the s32 at 0x84 and
  the 16 bits at 0x86.
- `CURRENT_ENTITY_LIT` (`LIT(Entity *, g_CurrentEntity)`) is the literal-address view for the `-O2` main
  program's literal `*(Entity **)0x800CAB14` reads.

### Enemy work areas

The entity bytes from 0x16C on (0x16C..0x18B) mean something different per enemy: each enemy's own "work
area". Each enemy file defines its struct at the top (`ZombieWork`: `hit_count`, `stagger_timer`, ...;
`HunterWork`, ...) and short macros built on `ENEMY_WORK` / `ENEMY_FIELD` / `ENEMY_MEMBER`:

- `ZOMBIE(e)->f`, e.g. `ZOMBIE(g_CurrentEntity)->hit_count` (the readable form);
- `ZOMBIE_FIELD(e, f)` and `ZOMBIE_MEMBER(e, f)` and `_AS(e, f, T)` variants: they reach the same field and
  only exist because the original code compiled differently.

A file that runs several entity kinds gets one struct per kind (`plant42.c`: `Plant42Work` +
`Plant42BodyWork`; `computer_arms.c`: `ComputerArmRightWork` + `ComputerArmLeftWork`). The structs come from
`config/enemy_work/` specs through `enemywork.py`.

### Struct views

Data reached through one pointer or global gets a struct and a short view macro, for example:

| view | struct | data |
|---|---|---|
| `ISCREEN` | `InteractiveScreen` | passcode panel (3x3 cursor, ...) via `g_InteractiveScreenStatePtr` (`ISCREEN->cursor_row`) |
| `CURRENT_ENTITY_LIT` | `Entity` | literal current-entity reads in the main program |
| `END_SLOT`, `END_DRAW`, `END_TEXT` | `EndingSlot` | ending (PC `EndSlot` + `TextureDesc` names; `END_SLOT->fade_level`) |
| `CL_LOGO` | `ClLogoSlot` | Capcom logo slots |
| `DOOR_CMD` | `DoorCmd` | door command interpreter (loop_depth, ip, loop arrays) |

| `SCRATCH_VEC` | `ScratchVec` | 0x1F8003D0 |
| `EFFECT` | `Effect` | the current `g_EffectPool` slot |
| `ROOM` | `RoomHeader` | the RDT header via `g_RoomData` |
| `TITLE_TMR` | | title timers (base `g_TitleTimers`) |
| `VIEWER_FIELD(path, T)` | `ViewerBlock` | item viewer block (`item.c`); keeps the original `&g_ViewerZoom` + constant form, the constant computed from field names |

Other view macros written with `LIT` / `LITP`: `NPC_CUR`, `WS_WEB_CUR`, `END_TBLK`. `formtry.py` rule sets

### Local pointer views

Local pointer variables and parameters get cast macros: `JOINT(sp18)->world.t[0]` (a skeleton joint;
`world.t` is its position in the room), `ENT(sp14)->health`, `BILLBOARD(arg0)->corners[2].vx`, `EFF(p)`,
`SCA(p)`, `FILESCR(p)`, ... (the variable names shown are the decompiler names from the specs' examples; the
code itself now uses real local names). Nested PS1 types (`SVECTOR` / `VECTOR` / `MATRIX`) and arrays
resolve to member paths; later array elements of a `stride` spec use the exact forms
`MEMBER_AT(p, W, path, T)` / `FIELD_AT(p, W, path, T)`. Variables keep their declared types.

Local-pointer specs exist for, among others, entity, model_object, joint, effect, effect_frame, sca_info,
map_screen, billboard, door_cmd_local, task_slot and the SCD opcode operands.

### Struct specs and global aliases

The specs in `config/structs`, `config/locals` and `config/enemy_work` generate the struct headers. A spec
names fields reached through globals, local pointers (`param <function> <variable>` lines), or global aliases
(`expr` rules, e.g. `g_RoomData_*`, `g_CurrentEntity_*`, `g_InteractiveScreenStatePtr_*`, `g_ClLogoCur_*`,
`g_DoorCmdCur_*`, `g_pRoomActionEntry_*`, `g_pScdEventCurrent_*`). `localview.py` emits each macro once, and
`enemywork.py` emits no unused view variants.

### `BYTES(n)` byte blocks

`BYTES(n)` (`struct { u8 b[n]; }`) is used for fixed-size copies and pointer steps that compile differently
with the real type. Such copies carry a comment.

### Raw byte-offset accesses

Raw accesses (`*(s32 *)((u8 *)e + 0x34)`) are invisible to the struct tools; `rawfield.py` hands them over
(see [rawfield.py](#raw-byte-offset-accesses-rawfieldpy)). Left as raw accesses on purpose: stream reads,
where a cursor advances by the bytes it reads (message control-code operands, animation/skeleton data
streams in `model.c`, op 0x3B's operands through the advancing script pointer).

## Declarations and aliases

### Placement of declarations

- **Block-scope declarations.** Sony prototypes and typed globals were copied into function bodies instead
  of sitting at file scope, because older functions declared the same Sony functions with m2c's guessed
  types in block scope, and a file-scope prototype next to them is an error. A call-cast workaround
  (`((T (*)(..))f)(..)`) is not an alternative: it changes how GCC 2.6.3 optimizes the call
  (`func_800479A4` (`scd_op_4b_bgm_stop_all`)). This is also why `re1_externs.h` is not included by source
  files.
- **File-scope prototypes change later callers.** A file-scope prototype changes the code of every later
  caller in the same C file, so block-scope `__asm__` aliases of functions and globals stand where a
  file-scope prototype or `extern` would seem natural.
- **Per-function `extern`s of globals** are moved to one block at the top of a C file by `declclean.py`
  where that compiles the same (aliases whose type differs stay). A global used through aliases can get a
  shared declaration in the program's `globals.h` where all aliases agree on the type (as `g_MenuWork` and
  `g_PlayerScale` did); aliases of globals defined in their own file or declared with another type in a stage
  `globals.h` stay ("conflicting types").
- **Struct typedefs used in a function signature** must be at file scope before the function. `integrate.py`
  keeps a draft's top-level `typedef` blocks and `#define`s at file scope in front of the function, but moves
  other draft declarations into the function body. Because of that, record tables inside a function use
  **anonymous** structs (`extern struct { s16 x, y; } D_X[];`), not typedefs.
- A file-scope prototype in a function's draft for a function defined in the same file is dropped by
  `integrate.py`; if the return type matters, use a block-scope declaration.
- From the time `INCLUDE_RODATA` was still in use: keep `INCLUDE_RODATA` blocks that other assembly
  functions still reference, and declare them `extern` in the C function that copies from them (e.g.
  `extern SVECTOR D_801054AC;`). No `INCLUDE_RODATA` is left in `src/`.

### Typed aliases of globals

Capcom's files declared the same global with different types (e.g. `g_XaVolume`, `D_800BEA2C`, is `u8` in
some functions and `s32` in `func_80015004` (`xa_set_volume`)). In one C file GCC 2.6.3 keeps the first type
(the conflict is only a warning), which changes the code. A function whose declaration disagrees with another
declaration in the file gets a **private alias** of the same symbol through a GCC asm label:

```c
extern s32 g_XaVolume_s32 __asm__("g_XaVolume");
extern u8 g_StageId_u8 __asm__("g_StageId");
extern u8 zombie_stagger_tbl_u8[] __asm__("zombie_stagger_tbl");
```

`integrate.py` adds these automatically (verified byte-identical). The alias reproduces the type a particular
original function saw for a global.

### Function aliases with another prototype

- **Callers that saw other prototypes.** A function may need a prototyped declaration of an already-defined
  function that differs from its definition (`s16 f(s32, s32)` while the file defines `s16 f(s16 a, s16 b)`;
  Capcom's caller saw other parameter types, so there is no truncation at the call). It keeps a private alias
  and its calls are renamed:

  ```c
  s16 f_p(s32, s32) __asm__("f");
  s32 xa_apply_mix_p(u8) __asm__("xa_apply_mix");
  ```

  This also applies when `f` is only *declared* at file scope (e.g. `void func_80015018(s32);`,
  `xa_apply_mix`). Dropping the alias changes the call code.
- **Prototype seen by Capcom's caller** (`void pad_update_l(void) __asm__("pad_update");`, `VSync_l`,
  `open_l`): reproduces the prototype the caller saw (e.g. `s32` for a `void` function).
- **Narrow-parameter definitions vs older callers** (`alias_old_decls` in `integrate.py`): when a function is
  defined with narrow prototyped parameters (`s8 f(s16 a, u16 b)`), every older function that declares `f`
  itself gets a private alias (`s8 f_a1() __asm__("f");`, calls renamed). Without it GCC 2.6.3 calls a local
  `f.NNN` (link error), and dropping the declaration would change the caller's argument code.
- **Return-type aliases**: a caller that needs a callee's result as `u8` while the file defines it
  differently declares `u8 f_u8() __asm__("func_X");`.
- **Suffixed declarations with another type**: per-function declarations under a suffixed alias name
  (`Flg_on_v`, `joint_move_v`, `g_EndingSlots_s32`) exist because Capcom's files declared the same function /
  global differently. Example: `void Flg_on_v() __asm__("Flg_on");`.

### K&R definitions and unprototyped declarations

Capcom often called functions without prototypes, so a definition `T f(void)` becomes K&R `T f()` when a
caller passes arguments. `void f();` without parameters stands where calls pass extra arguments.
Unprototyped declarations and function pointers stay as they are. `tools/argcheck.py` lists calls whose
argument count differs from the callee's definition (fine on the PS1 with its register calling convention, a problem for any other compiler or platform).

### Element aliases

-O2 code that addressed one array element as its own symbol gets an element alias:

```c
extern s32 g_PacketArea_1 __asm__("g_PacketArea+4");
```

Element aliases are listed in `config/elemfield_syms.txt`, which the warning fixers respect.

### Removing aliases

Block-scope `__asm__` aliases remain only where they are needed for the byte match. `aliastry.py` removes
every alias that compiles to the same bytes; `funcaliasclean.py` and `declclean.py` only handle identical
types (see [Declaration tools](#declaration-tools)).

## Forms that look odd but must stay

Much of the matched C contains constructs that look redundant or like leftovers but steer GCC 2.6.3 to the
original bytes. Do not "clean them up" without rebuilding and checking that all 13 executables still match.
The reasons are in the [matching guide](matching_guide.md).

### Addresses and symbols

- **Numeric addresses** behind `LIT` / `LITP` / `ADDR_`, including the scratchpad, instead of declared
  symbols: literal addresses (`*(s32 *)0x1F8003D0`, `((T *)0x800C3024)[i]`, `((Rec84 *)0x800C3000)[i]`,
  `((GsOT *)0x800C88A0)[buf]`) next to named symbols, where the original used numbers. The assembler expands
  the two forms differently (see [Fixed RAM addresses](#fixed-ram-addresses-and-the-scratchpad)).
- `LAB_SCROLL_X(T)` in `computer_lab.c` instead of the symbol `g_LabSlidesScrollX`.
- **Separate symbols that overlap a struct**, such as `g_MenuFlags` (`g_MenuWork` + 3), and per-field player /
  menu globals at -O2 sites where the struct form compiles differently (`g_PlayerHitState`, ...).
- **Per-function `__asm__` aliases**, including element aliases `__asm__("base+offset")` (see
  [Declarations and aliases](#declarations-and-aliases)).
- **The `g_ApiCallPtr` call idiom** in overlays: `(g_ApiCallPtr = api_x)(...)` (`g_ApiCallPtr` =
  0x801FEC18). More generally in `-O0` overlays: `(D_801FEC18 = D_801FExxx)()` call-through-assignment.

### Field access

- **Exact-form macros** (`ENEMY_FIELD`, `ENTITY_AS`, `MEMBER_AT`, `FIELD_AT`, `_AS` variants,
  `ENTITY_STATE_WORD`, and the `OFFSET_MEMBER` / `OFFSET_DEREF` forms they are built on) reproduce
  pointer-arithmetic accesses and type-punned reads that a plain member would compile differently.
- **Member-form accesses** (`M2C_SFIELD` in drafts, `OFFSET_MEMBER`) where a plain pointer cast would seem
  equivalent, and **pointer-arithmetic accesses** (`M2C_PFIELD` in drafts, `OFFSET_DEREF`) in the main program
  where the struct form changes -O2 scheduling.
- **Numeric sizes** (`ENTITY_SIZE`, `JOINT_SIZE`, `EFFECT_SIZE`) instead of `sizeof` (`sizeof` is unsigned and
  compiles differently).
- **`BYTES(n)` copies and pointer steps**; `ZombieHitThresholds` copied by value.
- **Stepping a pointer by a record size** with GCC's post-increment `move`. This was first written as a cast
  lvalue, `((struct { u8 b[0x7C]; } *)p)++;`. Cast increments are an old GCC-only form, and they were
  rewritten byte-identically so a modern GCC parses every file (no cast increment is left in `src/`; see
  [Warning-free, valid GNU C89](#warning-free-valid-gnu-c89)). The record-size step itself must stay.
- **Pointer adjusted in a separate statement**, e.g. `p = base; p = (T *)((u8 *)p + 0x744);`. Merging it into
  one expression folds the offset into the stores and changes the code.

### Expressions and statements

- **Statement expressions** `({ ... })` around constants or sub-expressions, such as `v * ({ bit * 2; })`,
  `({ -0x400; })`, `tbl[({ x - 1; })]`, `if (!({ (s32) x--; }))`: they block GCC's `fold()` from
  re-associating, folding or narrowing loads, and change the compiler's register choices. Capcom most likely
  used macros built on `({ ... })`.
- **`do { ... } while (0);` wrappers and temporaries holding a constant**: they change allocation weights or
  act as barriers.
- **A dead `register` variable in its own block** before a block copy: `{ register Bytes32 *p = &sp18; }`
  (probably a macro in Capcom's source).
- **Code duplicated into both arms of an `if` / `else`**: it is cross-jumped back into one copy, but the
  duplicate changes allocation or keeps the original's branch shape.
- **`goto`-built loops** next to real `while` / `for` / `do` loops (only real loops carry loop notes).
- **`goto` labels placed right after another label**, which produce a lone `nop`.
- **Dead stores** to locals that are never read (`sp14 = p->x98;`).
- **Sign-changing casts in tests** (`if ((u32) p->x-- == 0)`), `x *= -1` instead of `x = -x`, `x * 0x10`
  instead of `x << 4`, `__builtin_abs()`.
- **Constant-false conditions** that keep a call's side effect (`if ((u32) call() < 0U) { ... }`).
- **`*(volatile T *)addr = tmp;`** to keep a store that the optimizer would otherwise drop.
- **In `-O0` overlays**: explicit `return;` statements (each emits `j <epilogue>`), `x++` instead of
  `x += 1`, and the exact set and order of local declarations (every local gets a stack slot).

### Stack frame and layout

- **Padding locals** (`s32 padNN;`, unused `s32 unused[N]` arrays in -O2 code) that only exist to give the
  stack frame its original size and layout.
- **Rodata pad words**: `__asm__(".section .rodata\n\t.word 0\n\t.text");` stands where one of Capcom's files
  ended or aligned a jump table (see the [matching guide](matching_guide.md)). They mark Capcom's original file
  boundaries; `tools/file_boundaries.py` maps such hints to code ranges.
- **`#JTALIGN2` lines** (`__asm__("#JTALIGN2");`) before a function mark a 4-aligned jump table (some of
  Capcom's are); `tools/jtalign.awk` handles them in the main program's build.
- **Line layout of duplicated code.** GCC 2.6.3 keeps line-number notes in the RTL even without `-g`, and
  cross-jumping sees them: reformatting an `if` / `else` whose two arms are the same call changed the
  generated code (main `func_8005905C` (`menu_item_view_model`)). Indentation is free, but rebuild after every
  layout change of duplicated code.

### Permuter output

Code produced by decomp-permuter can contain permuter tricks (`new_var = 4;`) and macro-expanded shapes; it
matches but should be tidied (and re-verified). When tidying, keep its tricks that are needed
(`do { x = b; } while (0);`, a temporary for a constant) and add a short comment.

### FAKEMATCH comments

A match that needs a compiler-only trick with no natural C equivalent carries a `/* FAKEMATCH: ... */`
comment explaining why; `grep FAKEMATCH` lists them. There are two:

- `func_8003E228` (`player_ctrl_behavior_walk_back`, `src/main/player.c`): an empty `__asm__("")`, an insn
  that emits no code, which keeps cross-jumping from merging;
- `func_80056FC0` (`menu_draw_health_bar`, `src/main/status_menu.c`): a volatile store, so CSE does not
  record it.

Replace them if natural C is found. Details: [matching_guide.md](matching_guide.md).

## Warning-free, valid GNU C89

### No compiler warnings

The build has no compiler warnings, and it must stay that way. The fixes that got it there are the patterns
to follow:

- declaration type mismatches: block-scope prototypes given the definition's type, PsyQ prototypes,
  `void f();` where calls pass extra arguments, per-function aliases where the match needs another type
  (`mmfix.py`, `aliasren.py`);
- casts to the declared type where a pointer is stored/passed as an integer or the other way round, or a
  pointer of another type is stored/passed (`castfix.py`);
- hand fixes such as `yawn_post_move`'s joint pointer as `u8 *`, `pad_vibration_count_active` as `u32`, the
  `RotAverage3` locals as `long`.

The warning fixers:

- `mmfix.py`: declaration conflicts (block-scope prototypes get the definition's type);
- `castfix.py`: casts to the declared type at assignments and calls;
- `aliasren.py`: renames one function's declaration to an `__asm__` alias.

```sh
python tools/castfix.py [--dry] files...
```

`castfix.py` takes the target type from the prototype in scope (`passing arg N of f`) or the declared type
of the left side (a plain name, `LIT(T, x)`, `*_AS(.., T)` / `FIELD_AT(.., T)`, or a struct field name with
one type in every struct). It only handles single-line statements. `mmfix.py` and `castfix.py` skip lines
with a symbol from `config/elemfield_syms.txt`. A cast between 32-bit types does not change the code, but
every edit is still checked per function with `hunkcheck.py` (see [hunkcheck.py](#hunkcheckpy)), which also
rejects edits that add warnings.

### Modern-GCC syntax check

The sources are plain GNU C89: a modern GCC (`mips64-elf-gcc -fsyntax-only -std=gnu89 -mabi=32`) parses every
file without errors. Old GCC-only forms such as cast increments `((Joint *)p)++` were rewritten,
byte-identically. `tools/syncheck.py` runs that check on every C file (after `make compile_commands`); it
must print `total errors 0`.

### Editor support (IntelliSense)

`make compile_commands` writes `compile_commands.json` with per-file flags; a `src/shared/` enemy file gets
the headers and stage `globals.h` its wrapper compiles it with. `.vscode/c_cpp_properties.json` points the
VS Code C/C++ extension at it (32-bit MIPS, GNU C89). Re-run it after adding or splitting files.

## Readability and structure tools

All tools run from `dualshock/` with the project venv Python (see [decomp_guide.md](decomp_guide.md) for the
interpreter path and the `../tools/buildenv.sh` environment). The short tool table is in the guide; this
section describes how the readability and structure tools work.

**The safety net.** Every tool that rewrites code verifies the result with a full split + clean rebuild of
every program that compiles the changed file (all 13 executables must match) and restores the old text on
failure, usually per function. Only one job per program at a time.

### Renaming: rename.py, ovlrename.py

```sh
python tools/rename.py func_8003BAF8=Pad_Update D_800CAB14=g_CurrentEntity ...
python tools/rename.py --file names.txt            # lines `OLD = NEW; // comment`
python tools/rename.py --target stage1 OLD=NEW ... # overlay-local symbol
```

`rename.py` writes the symbol-file entry (`config/symbol_addrs.txt` for the main program, which the overlays
also read, or `config/symbol_addrs_<target>.txt`; data symbols get no type) and replaces OLD in `src/`,
`include/`, the header specs (`config/structs`, `config/locals`, `config/enemy_work`), `config/addrs.txt` (a
name that is only a fixed-address name gets no symbol entry; `ADDR_x` uses are renamed too), the per-function
alias variants (`OLD_l`, `OLD_a1`, ...), `__asm__("OLD")` strings and comments. For an overlay symbol it also
edits `include/`; overlay symbols are checked and renamed only within that overlay. It deletes the old
`asm/.../OLD.s` (splat never does). Then `make split`, a clean build; all 13 must match, otherwise everything
is restored. Bad pairs are skipped instead of aborting a batch. It cannot do one name across several stages
plus a shared source in one call; that is what `ovlrename.py` is for:

```sh
python tools/ovlrename.py OLD=NEW ...
python tools/ovlrename.py --file renames.txt        # lines `OLD = NEW; // why (evidence)`
```

`ovlrename.py` renames an overlay symbol in every overlay at once, including `src/shared/` (a function in
`src/shared/<enemy>.c` is listed in the symbol file of every stage that compiles it). It appends the evidence
to `config/names_overlays.txt`, skips a pair whose OLD also appears in main-program files, and prints mentions
in `config/locals/*.txt` as FOLLOW-UP.

After renaming local variables, update the local-pointer specs' `param` lines with

```sh
python tools/specvars.py <rename log> [more logs]   # log lines: `<file> <function> <old> <new>`
```

### Struct fields: fieldrename.py

```sh
python tools/fieldrename.py <batch file>      # lines: `Struct old_name new_name   # comment`
python tools/fieldrename.py --fast <batch>    # incremental build; only for renames inside .c files
```

The same placeholder name (`unk14`) exists in many structs, so a text search cannot tell the uses apart. The
compiler can: the tool renames the definition (the spec line in `config/structs|locals|enemy_work` with
`struct X`, or the typedef block `} X;` in `include/` or `src/`), regenerates the headers, runs `make -k`,
renames every reported "structure has no member named `old'" line, and repeats. A clean build must match,
else everything is restored. Notes:

- One old name per round, so a line cannot mix up two structs' fields. A line that uses the same old field of
  two structs (`E12.x0` and `E1C.x0`) needs both renames in one batch (the same new name is allowed).
- Parallel make can glue two error messages together; the tool takes the last `src/` / `include/` path before
  `:line:`.
- A view macro inside a spec (`CL_LOGO->unk18`) must be renamed by hand; `config/enemy_work` specs have no
  `struct` line and are renamed by hand.
- Header changes need the clean build (no `--fast`).

### Name lists: mergenames.py

`python tools/mergenames.py <survey folders...>` turns survey files (`survey.tsv` functions, `globals.tsv`
globals) into `config/names_main.txt` (`func_X = name; // subsystem, confidence: evidence`) and
`config/globals_main.txt` (`D_X = g_Name; // type guess, confidence: evidence`). Only high/medium confidence
names are active; low ones are commented out. Rejected: invalid identifiers, C keywords, names already used,
duplicates, globals inside the player entity (0x800C5124-0x800C52A3, which become struct fields instead), and
names that no longer exist.

### Names across overlays

- `python tools/twins.py [--groups out.tsv]` fingerprints every function's assembly (mnemonics, registers,
  constants kept; labels, symbol names and absolute addresses abstracted). Functions with the same fingerprint
  do the same thing. The 1,468 overlay functions are 626 distinct codes (50 groups appear in 6 stages, 109 in
  3, 174 in 2, 258 are unique).
- `python tools/nametwins.py --file names.txt [--dry-run]` (lines `<program> <current name> = <new name>; //
  evidence`) gives a function and all its twins the same name, **only when the code is unique in every
  program**: generic tiny functions (empty functions, thunks, table dispatchers) share fingerprints (otherwise
  `title_nop` / `ending_nop` would be named `zombie_no_action`).
- `python tools/tableprop.py [--apply]` pairs dispatch tables of named overlay functions with the PC
  namesake's table on the same entity field, by position (only consistent pairings); it repeats until nothing
  new is found.

### Declaration tools

- `declclean.py` moves the per-function `extern` declarations of globals to one canonical block at the top of
  a C file and reverts any function whose bytes change. Rules: canonical type = file-scope type, else the most
  common plain type, else the most common alias type; a function that declares another type gets a typed
  alias; the full array suffix is kept (`[][6]`); `extern ... func_X;` (function address uses) and defined
  functions are never moved; globals with any declaration the tool cannot parse (inline `struct {...} *X;`,
  function pointers `void (**X)(void);`) are left alone.
- `funcaliasclean.py` replaces per-function function aliases by the real name when the prototypes are
  identical.
- `aliastry.py` removes per-function `__asm__` aliases wherever the real name compiles to the same bytes even
  if the types differ: per function all at once, then one at a time, every step verified by a build.

### Entity fields: entityfields.py, entityas.py, playerfields.py, playersyms.py

- `python tools/entityfields.py --target stageN [--loose]`: makes `g_CurrentEntity` an `Entity *` (pointer
  arithmetic gets a `(u8 *)` cast; `Entity *` aliases merged per function) and turns field macros on it into
  `->field` where Entity has a field there with exactly that type (`--loose`: also the other signedness, kept
  only where the function still matches). Pointer-arithmetic accesses are left alone.
- `python tools/entityas.py <C file> ... | --all`: the remaining `g_CurrentEntity` accesses of any type,
  readable first (`g_CurrentEntity->f`, a cast when read with another type, plain when written), exact
  fallback `ENTITY_AS(e, f, T)` (member form) / `ENTITY_FIELD(_AS)` (pointer form); addresses such as
  `(u8 *)g_CurrentEntity + 0x34` become `&g_CurrentEntity->pos_x`. Checked per function in every program.
- `python tools/playerfields.py --target X [--loose]`: replaces separate symbols inside the player object
  whose type matches the Entity field by `g_PlayerEntity.<field>`; unused file-scope declarations are dropped.
- `python tools/playersyms.py <C file> ... | --all`: the rest of the player-object symbols of any type
  (`D_800C51AE` = `hit_state`): same type -> `g_PlayerEntity.f`; same size -> cast on read, plain on write;
  `&sym` -> `&g_PlayerEntity.f`; s32 at 0x84 / 16 bits at 0x86 -> `ENTITY_STATE_WORD` /
  `ENTITY_ACTION_*(&g_PlayerEntity)`; fallback exact `(*(T *)&...)`, then the old text (some -O2 main-program
  cases). Unused aliases and `globals.h` declarations are removed. Literal-address uses are left alone.
  Checked per function in every program that builds the file.

### Enemy work structs: enemywork.py

```sh
python tools/enemywork.py survey <enemy file>          # offsets, types, counts, example uses
python tools/enemywork.py apply <enemy file> <spec>    # struct + macros, rewrite, verify
```

`survey` shows how an enemy file uses the entity bytes 0x16C.. (its work area). Spec
`config/enemy_work/<enemy>.txt`:

```
struct ZombieWork ZOMBIE            # struct name, macro prefix
0x06 s16 move_timer   comment...    # offset from 0x16C, type, field name
skip plant42_body_*                 # functions of another entity kind in the same file - left alone
only plant42_body_*                 # the opposite (a second spec for that kind; apply both)
```

`apply` writes the struct and macros (`ZOMBIE(g_CurrentEntity)->hit_count`), rebuilds every program that
compiles the file and, per changed function, falls back to the exact `_AS(e, f, T)` forms, then to the
original text. Accesses through other pointers (other objects, offsets up to 0x55C) are left alone.

### Struct views: structview.py

`structview.py` gives a struct to data reached through one pointer or global (the views listed in
[Struct views](#struct-views)), writes `include/re1_views.h` and rewrites the code.

```sh
python tools/structview.py header                       # regenerate include/re1_views.h from all specs
python tools/structview.py apply config/structs/x.txt   # header + rewrite every file that uses the base
```

Spec format:

```
struct InteractiveScreen                                   # the struct type
view ISCREEN = ((InteractiveScreen *)g_InteractiveScreenStatePtr)   # short macro for the pointer
base g_InteractiveScreenStatePtr                           # expression in the code (1+ lines per view)
define                                                     # write the typedef from the lines below
0x04 s32 cursor_col   # comment                            # offset, type, name
```

or `fields Entity [max 0x16C]` for a struct already in a header. Field names starting with `pad<hex>` /
`sub<hex>` are treated as padding (not names like `substate`). Every rewrite is checked per function.

### Local pointer views: localview.py

```sh
python tools/localview.py header                      # regenerate include/re1_locals.h from all specs
python tools/localview.py apply config/locals/x.txt   # header + rewrite every file
```

Spec keywords:

- `struct` / `macro` (e.g. `JOINT(p) = ((Joint *)(p))`), `define` or `fields Entity`;
- `source <regex>`: a variable qualifies when **every** assignment to it in the function matches (e.g.
  `sp18 = g_CurrentEntity->joints` for Joint); also per use, for variables m2c reuses. The entity regex must
  match the whole right-hand side (so `victim->joints` is not taken for an entity); `x = JOINT(..)->anim_slot`
  must not qualify;
- `stride` (arrays: offsets past one element are later elements `[k]`), `max`;
- `param <function> argN` / `param <function> <variable or expression>`: parameters chosen by hand from the
  offsets used and the call sites;
- `expr` (base expressions), `noaddr` (script records: `p + N` is the next operand, not a field address, so
  `p + N` is left alone);
- `file` / `exclude` (path regexes; e.g. the entity specs `exclude shared/yawn\.c$` because yawn stores joint
  pointers in `aim_target`, covered by `config/locals/yawn_joint.txt`).

Behaviour: balanced-paren base parsing; offset bases only for stride specs (an entity's `(e + 0x16C)` is the
enemy work area) and never from inside a call/member (`JOINT(arg0)->anim_slot` is not `arg0 + N`); per-use
flow typing for variables m2c reuses (the nearest assignment dominates the use and no loop re-assigns it);
`*X = v` writes through X and reads X itself. Checked per function.

### Raw byte-offset accesses: rawfield.py

```sh
python tools/rawfield.py to [files...]    # raw byte-offset accesses -> OFFSET_DEREF(base, T *, off)
python tools/rawfield.py back [files...]  # every OFFSET_DEREF left -> raw form again
python tools/rawfield.py count            # how many raw byte-offset accesses are left
```

Accesses written by hand as `*(T *)((u8 *)X + 0x34)`, `*(T *)(bytes + 0x34)` (bytes a u8/s8/char/void
pointer), `((u8 *)X)[0x34]`, `((T *)X)[k]` for 2/4-byte T, or plain `bytes[k]` reads of byte pointers are
invisible to the struct tools. `to` rewrites them into `OFFSET_DEREF` (the same byte arithmetic, so the code
does not change), the specs' `apply` (`localview.py` / `structview.py`) names what they know
(`ENT(e)->pos_x`), and `back` returns the rest. Details:

- global aliases used as byte pointers (`extern u8 *g_X_l __asm__("g_X")`) are recognised;
- `bytes[k]` uses the variable's declared element type (signed for s8/char);
- declarations are skipped (`char s[6];` inside a local typedef must not be rewritten);
- `to` keeps a journal under `temp/`, so `back` restores the exact original text (a `to` + `back` round trip
  gives identical sources); the fallback form is parenthesised (`X[1]++`).

([decomp_guide.md](decomp_guide.md) says `to` produces `M2C_PFIELD`; the tool's own description says
`OFFSET_DEREF`.)

### Fixed addresses: litaddr.py

See [Fixed RAM addresses and the scratchpad](#fixed-ram-addresses-and-the-scratchpad).

### Rule-driven rewrites: formtry.py, ply84.py, sfield.py

- `formtry.py`: rule-driven readability rewrites (regex -> replacement) verified per function: rewrites every
  site, builds, and where a function's bytes change retries one site at a time, keeping every rewrite that
  matches (used for `EFFECT->`, `EFFECT_AT`, the player / MenuWork struct forms).
- `ply84.py` and `sfield.py` are rewrite rules (for `trybatch.py`) for the effect pool records and the
  member-form field access; see the [matching guide](matching_guide.md).

### Analysis helpers: infer_struct.py, api_table.py, file_boundaries.py

- `infer_struct.py <symbol>`: collects every field offset and type used on a pointer across all drafts. Use it
  to design a struct for a symbol.
- `api_table.py`: decodes the 183-entry overlay engine API table (0x801FE900) (`--md out.md` writes a Markdown
  table).
- `file_boundaries.py`: maps splat's rodata split hints to code ranges, to estimate where Capcom's original
  source files begin and end.

### Topic files: splitplan.py, splitc.py, splitfile.py

```sh
python tools/splitplan.py wish.txt plan.txt        # `<first function> <file name>` per line
python tools/splitc.py [--target main|stage1|...] plan.txt
make split && make;  python tools/splitc.py [--target ...] --pad;  rebuild until no padding changes
python tools/splitfile.py <file> <first function of part 2> <part 1 name> <part 2 name> "<part 2 header>"
#   e.g. python tools/splitfile.py enemy_path set_initial_items enemy_path inventory "Inventory and item box"
```

- `splitplan.py` checks and moves the file boundaries of the main program (8-aligned jump tables): it moves
  invalid file starts to the nearest function that keeps both neighbouring files' rodata valid.
- `splitc.py` splits one program's big C file into topic files without changing a byte: it writes the files,
  `globals.h`, the prototype blocks, the yaml subsegments and the rodata piece folders; `--pad` adds the
  original padding between files (`.space N` gaps).
- `splitfile.py` splits one existing main-program topic file in two at a function boundary (optionally
  renaming the first part). Run it after `make split` (so `asm/main/nonmatchings/` is current). Part 2 starts
  with part 1's includes and its "functions defined in the files before this one" block, prototypes of the
  part-1 functions it uses, and the file-scope typedefs / macros / declarations it needs; functions defined
  later stay unseen. The yaml gets a `c` subsegment for part 2 and `.rodata` subsegments at each part's first
  rodata item. The tool wraps headers. Then a re-split and clean build; it restores on failure.

Splits made with `splitfile.py` include:

- `enemy_path.c` -> + `inventory.c`;
- `sound.c` -> + `stage_load.c`;
- `file_reader.c` -> + `file_pickup.c`;
- `screen.c` -> `clut_fade.c` + `keyconfig.c` + `camera.c`;
- `entity.c` -> `spiderweb.c` + `entity.c`;
- `entity_common.c` -> `game_reset.c` + `entity_common.c` + `tyrant_trail.c`;
- `message.c` -> `message_actions.c` (the `g_MessageActionFuncs` entries) + `message.c`;
- `interactive_screen.c` -> `interactive_screen.c` (dispatcher + passcode panel) + `computer_lab_terminal.c`
  (the lab terminal's state machine, right before `computer_lab.c` with its drawing).

### Twins across overlays

Many overlay functions exist in near-identical copies in every stage (e.g. the `func_8010F7FC` family, the
`func_80106F44` and `func_8010574C` families, the `func_80109CD4` family).

- `propagate.py` copies a matched stage function to its identical twins in the other stages.
- `port.py src_t src_f dst_t dst_f out.c` copies one to a near twin (symbols paired in order), and
  `twinhunt.py` searches all stages for near twins of matched functions and tries them.
- `sharetwins.py` (after the stages are split per enemy): for every enemy file present in two or more stages
  it writes `src/shared/<enemy>.c` once (the text most stages match wins), turns each stage file into a
  wrapper, rebuilds all programs, keeps a stage's own copy if its bytes change, and undoes a shared file used
  by fewer than two stages. It is safe to run again (`full_text()` expands an existing wrapper with its shared
  file).

### hunkcheck.py

`hunkcheck.py` verifies source edits per function: it rebuilds the changed files, compares each function's
assembly with a saved baseline and rolls back the edits of every function whose code changed or that gained
warnings. It keeps its baseline and state in `../temp/warn/`.

### Work copies: workcopy.py

```sh
python tools/workcopy.py create <name>   # ../work_<name>/: copy of the sources, split + built
python tools/workcopy.py diff <name>     # patch of the copy's changes since create (written under temp/)
python tools/workcopy.py apply <name>    # apply that patch to dualshock/, split, clean build;
                                         # restores dualshock/ if anything fails to match
```

A work copy is a private copy of `dualshock/` for parallel work. It sits next to `dualshock/` (the root
`.gitignore` has `work_*/`) and builds on its own. Only `src/`, `include/` and `config/` are compared and
merged; conflicting hunks are applied by hand. When several copies change the generated headers or shared
specs, apply each patch excluding those files, merge the spec lines by hand, regenerate both headers
(`structview.py header`, `localview.py header`) and do a full build. After a merge, do a clean build, a fresh
tree and check that the generated headers regenerate identically.

### Audit scripts

- `audit_scan.py` counts leftover decompiler patterns (`D_` / `func_` names, `unk` fields, m2c locals, ...)
  per folder.
- `audit_unused.py` lists file-scope declarations and `#define`s that nothing uses.
- `argcheck.py` lists calls whose argument count differs from the callee's definition.
- `syncheck.py`: see [Modern-GCC syntax check](#modern-gcc-syntax-check).

m2c tags such as `/* irregular */`, `/* switch N */` and "Duplicate return node" are removed from the sources.

### Game-data helpers (project `tools/`)

- `tools/rdt_em_set.py` walks every `ROOM*.RDT` init script and lists the EM_SET (enemy/NPC placement)
  commands. Its opcode-length table lacks op 0x33 (variable length), so its walker stops there.
- `tools/emd_tim.py` renders an EMD model's TIM texture to identify the model.

## Building a disc image

`dualshock/build_disc.bat` (double-click it) compiles the 13 executables and builds a disc image laid out
like the original Dual Shock (USA) dump: `(Track 1).bin` (data) + `(Track 2).bin` (CD audio) + `.cue`, in
`dualshock/build/disc/`. A full run (clean rebuild + disc) takes about 10 seconds. The image can be played in
an emulator (open the `.cue`).

1. `dualshock/tools/build_disc_make.sh` (MSYS2 bash from `tools/external/msys64`, the same environment as
   `tools/buildenv.sh`) runs `make clean` + `make -j8`. The full compiler output goes to `build/make.log`; only
   the `OK` / `MISMATCH` lines (and errors) are shown.
2. `dualshock/tools/build_disc.py` (with the mkpsxiso tools in `tools/external/mkpsxiso`):
   - on the first run, unpacks the original disc into `build/disc_work/` with
     `dumpsxiso -q -e pcm -x extracted -s layout.xml <original cue>`. `-e pcm` keeps the CD-audio track
     bit-exact; the XML keeps the file order, dates, license sectors, the 149+1 dummy sectors and the
     `ZNULL.DAT` DA entry pointing at track 2;
   - copies `build/SLUS_007.47` and `build/*.EXE` over `extracted/SLUS_007.47` and `extracted/PSXUSA/PROG2/`;
   - runs `mkpsxiso -y -o image.bin -c image.cue layout.xml`, which gives one bin with both tracks. It is split
     at track 2's INDEX 00 (65:18:30 = sector 293880 = 691,205,760 bytes), so `Track 2.bin` starts with its
     2-second pregap, exactly like the original dump. The cue is written with CRLF line endings like the
     original;
   - prints the CRC32 of each output file next to the original's, if found (`MATCH` / `DIFFERENT`).

mkpsxiso rebuilds the unmodified disc bit-identically (both tracks). With the decomp's executables all three
files have the original CRC32s: Track 1 `B01860CE`, Track 2 `7976083E`, cue `B6D92E22`. The game's assets
(movies, sounds, rooms, ...) and the audio track come from the original disc.
